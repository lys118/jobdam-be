# ![JobDam](logo.png) - Ai 기반 실시간 모의면접 매칭 서비스

## 📝 개요

### 목적
모의 면접의 '번거로움'을 없애고, '효율적인 준비'를 돕는 실전형 플렛폼

### 타겟
취준생, 이직자 등 취업대상자

### 기능 및 특징
1. 유저들끼리 매칭을 통해 모의면접을 진행한다.<br>
  - 이 과정에서 면접자+면접관 역할을 동시에 수행할 수 있다.(면접관 간접체험가능) 
2. 이력서를 업로드하면 AI가 추천질문을 생성해준다.
3. 화상 모의면접이 끝나면 피드백을 AI가 분석해준다.


## 🛠️ 기술스택

### **Backend**
- Spring Boot 3.x (REST API)
- Spring Security (JWT 기반 인증/인가)
- WebSocket (STOMP, SockJS) – 실시간 채팅/화상면접 시그널링
- MySQL (관계형 DB)
- Gradle (빌드/의존성 관리)

### **Infra & DevOps**
- **AWS**
  - EC2 (백엔드 서버)
  - S3 (정적 파일, 프론트엔드 배포)
  - CloudFront (CDN, HTTPS)
  - Route 53 (DNS)
  - RDS (MySQL 관리형 DB)
- Nginx (리버스 프록시, TLS/HTTPS 인증서 관리)
- Let's Encrypt (무료 TLS 인증서)
- Coturn (STUN/TURN 서버 – WebRTC NAT traversal)

### **매칭 페이지**<br>

1. 매칭 조건은 신입/경력, 직군, 세부직군, 매칭인원수(1:1,3~6,상관없음) 4가지이며

4. 3~6명방은 3명의 인원수가 모일 시 3명채팅방이 개설되어 진입하게 되며
5. 방에 추가인원이 들어오는 식으로 구성되어 있다.
6. 방에서 나가면 같은방에는 1분뒤에 재입장이 된다.

### **화상 모의면접 페이지**<br>
![화상 모의면접 GIF](./asset/videochat.gif)

## 🤔 문제점 
### 웹소켓 구조설계시 jwt인증
1. 처음에 handshake 과정에서 JWT를 검증하려 했으나 실패  
   - 이유는 handshake 과정은 HTTP로 시작해서 WebSocket으로 업그레이드하는 단계인데,  
   - 이때는 STOMP 메시지(예: CONNECT)가 서버로 전달되지 않아서  
   - JWT 정보 등 실제 인증에 필요한 데이터를 확인할 수 없다.

2. 해결 방법  
   - WebSocket 연결 후, 클라이언트가 STOMP CONNECT 프레임을 보낼 때  
     JWT를 커스텀 헤더로 실어서 전송한다.
   - 서버에서는 `ChannelInterceptor`(preSend)에서 해당 JWT를 검증하고  
     검증이 성공하면 `Principal`에 유저 정보를 저장하여 이후 인증 정보를 활용한다.

### 웹소켓 통합구조설계
1. 처음 프로젝트 진행시 매칭,채팅 담당팀원과 화상채팅 담당이 따로 있었는데
   같은 웹소켓을 사용하기때문에 세션관리 이벤트 구독관리등 많은 충돌 발생될거 같았음 

2. 해결 방법
    - 인터셉터에서는 오로지 jwt인증만 담당시킨다.(역할분리)
    - 세션트래커를 별도로 설계하고 매칭, 채팅, 화상채팅등 각 도메인에 따라
    - 독립적으로 세션,이벤트를 관리하도록 구조화함<br>
    ex) 공통: WebsocketSessionTracker(인터페이스), Chat,Matching,WebRtcSiginalSessionTracker로 구분

### 웹소켓 상태관리
1. 단순 채팅방에 들어갔다 나왔다 하는것이 아닌 매칭-> 채팅-> 화상채팅으로 진행이 되어
   기존의 정보를 가지고(매칭정보,인원수 등) 다음단계로 진행을 해야하기에 상태관리가 필요했다.
   상태관리를 안하게되면 새로고침이나 인터넷 끊김등과 실제로 나간것을 구분하지 못하는 상황이 발생한다.

2. 해결방법
   - 유저에게 별도의 상태(connect)를 추가하여 스케쥴을 통하여 일정시간이 지나면 방에서 추방하는 방식사용.

3. 추후에 기회가되면 핑퐁도입이나 메세지큐 도입을 통해 실시간성을 더 높일계획

## 💬 회고
스위프 웹9기에 참여하여 진행한 프로젝트

### 1. 기획 및 사전조사의 중요성
- **AI 비용 문제를 간과**  
  - 이력서 분석 등 AI API 사용 시, 건당 수십 원의 비용이 발생하는 것을 프로젝트 중간에야 알게 됨  
    API사용 말고 직접 모델을 구축하면 서버(특히 고성능 GPU) 비용 부담이 큼  
  - 단기적으로는 스위프 지원으로 네이버 Clova API를 무료로 활용하여 해결  
  - 장기적으로는 **결제 시스템** 도입 등 비용 회수 방안이 필요함을 느낌

- **초기 유저 수 부족 시 매칭의 한계**  
  - 단순 “실시간 매칭”만으로는, 일정 인원 이하에서는 매칭이 거의 불가능하거나 대기 시간이 길어짐  
  - 해결 방안으로,  
    - **면접관/면접자 역할을 명확히 구분**하고  
    - 면접자가 원하는 면접관에게 직접 신청하는 방식  
    - 또는 매칭 시간을 넉넉히 주고, 매칭이 되면 문자/카톡 등으로 알림을 보내주는 방식 등을  
      차후 개선 방향으로 논의함

### 2. 초반에 설계의 중요성
- **type 설계 미흡**
  - 프론트엔드와 백엔드 간에 데이터 타입을 명확하게 맞추지 않고 개발을 진행하다 보니,
    서로 다른 타입의 데이터를 주고받으며 잦은 버그와 혼란이 발생했다.
  - 이를 통해, 개발 초기에 명확한 타입 설계와 팀원 간 소통이 매우 중요하다는 점을 깨달았다.

### 3. 프로젝트를 마치며

비록 팀 인원이 부족했지만, 끝까지 포기하지 않고 협력하여 프로젝트를 무사히 완주할 수 있었다.  
온라인 협업이 처음이라 소통이 잘 안될까 걱정했지만, 예상과 달리 팀원 간 의사소통이 매우 원활했고,  
질문을 남기면 거의 즉시 답변이 올 정도로 활발하게 소통하는 경험을 할 수 있었다.  

프로젝트 수료식 날, 다른 팀의 이야기를 들어보니 답변이 느려 어려움을 겪은 경우도 많았다고 한다.  
소통이 잘 되는 팀원들을 만나 다행이라고 느꼈고,  
프로젝트에서 가장 중요한 것은 **커뮤니케이션**임을 다시 한 번 깨달았다.

아쉬웠던 점은,  
새로운 기술을 최대한 많이 경험해보고 싶었지만, 인원 부족으로 프론트엔드까지 병행하다 보니  
시간이 부족해 충분히 도전하지 못했다는 점이다.  
다음 프로젝트에서는 **Docker, CI/CD, 메시지큐 등 다양한 기술도 적극 도입**해보고 싶다.
